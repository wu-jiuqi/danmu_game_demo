# 《百味饭馆》H5页游实现方案 v1

> 面向 24 小时技术面试 Demo。目标是让评审打开页面后，立即看到“客人到访 → 排队/落座 → 点单 → 烹饪 → 出餐 → 结账 → 研发/升级”的可玩闭环，并能用模拟弹幕和礼物改变状态。

## 1. 方案结论

推荐使用 **React + TypeScript + Vite + Vitest**：

- React 只负责渲染和交互，所有规则集中在 `game-engine`，避免把状态写死在 UI 组件里。
- TypeScript 适合表达“队列、桌位、灶眼、订单、礼物效果”等有限状态，降低 24 小时内的状态污染风险。
- Vite 提供离线可运行的构建产物；Vitest 覆盖概率、容量、超时和礼物上限等关键规则。
- 不接后端、不接真实抖音 SDK；用本地事件适配器模拟评论/礼物/点赞，未来可以替换为直播平台适配器。

GDD 已冻结的 24 小时范围优先级：

1. **P0**：统一 Tick、客人/座位/灶眼/订单闭环、localStorage、资源栏、日志、暂停与倍速。
2. **P0**：五种礼物的规则和边界，尤其是仙女棒 4 根封顶、魔法镜 3 层、甜甜圈 180 秒上限、炸弹冷却和容量检查。
3. **P0**：研发、饭馆升级、厨师升级和 12 道菜的数据驱动配置。
4. **P1**：借鉴座位排序的可视化，把队列和桌位做成可读的“位置管理”区域；只有 P0 的 14 个验收用例通过后，再增加拖拽或 `排1/排2/排3` 优先级指令。

## 2. 对抖音弹幕游戏和参考案例的判断

抖音官方将直播玩法描述为由直播间评论、礼物、点赞等事件驱动，并实时反馈到独立玩法客户端；评论指令可以配置为完整匹配或包含匹配，礼物也需要对应明确效果。[直播玩法简介](https://partner.open-douyin.com/docs/resource/zh-CN/interaction/introduction/live-play/1) ｜ [评论指令配置](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/introduction/zn/toybox-start) ｜ [礼物互动能力](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/jierushuoming/hudongshuju/liwushuju)

因此 Demo 采用“事件适配器”而不是把弹幕直接写进业务逻辑：

```text
模拟弹幕/礼物按钮
        ↓
CommentAdapter / GiftAdapter
        ↓
统一 Command（JOIN、SERVE、GIFT_*、UPGRADE_*）
        ↓
GameEngine.dispatch(command)
        ↓
1 秒 Tick 推进 GameState
        ↓
React 订阅 state，渲染餐厅、资源和日志
```

公开资料能确认《喵了个鱼》是抖音弹幕互动钓鱼玩法，但无法可靠核实其完整规则或“座位排序”的具体机制。因此只借鉴它的**竖屏观看构图、短指令、实时反馈和轻量榜单**，不复刻名称、素材、数值或未公开规则。[抖音视频](https://www.douyin.com/video/7312746004762184997) ｜ [B 站内测介绍](https://www.bilibili.com/video/BV1ge411Z7ii/)

座位排序在本项目中的转译是：把排队位、桌位、灶眼、待出餐位做成可数的空间资源，让观众一眼看见“谁在等、哪桌空、哪道菜卡住”，再用 `出餐` 或可选的 `排1/排2/排3` 指令产生可见变化。

## 3. 核心状态模型

`GameState` 是唯一事实来源。UI、动画和日志都不能自行倒计时或修改资源。

```ts
type GameState = {
  clock: { tick: number; paused: boolean; speed: 1 | 2 | 5 };
  resources: { cash: number; red: number; green: number; blue: number; badges: number };
  progress: {
    restaurantLevel: 1 | 2 | 3;
    chefLevel: 1 | 2 | 3;
    activeDishIds: string[];
    publishedDishIds: string[];
    pillDrawCount: number;
  };
  runtime: {
    queue: Guest[];
    seats: Seat[];
    stoves: Stove[];
    readyOrders: Order[];
  };
  effects: {
    mirror: { layers: 0 | 1 | 2 | 3; remaining: number };
    donutRemaining: number;
    wizardCooldown: number;
    bombCooldown: number;
  };
  stats: { todayGuests: number; todayRevenue: number; logs: LogEntry[] };
};
```

### Tick 处理顺序

每秒只推进一次逻辑；倍速只是一次帧内执行 1/2/5 个固定 Tick：

1. 计算客流间隔，生成客人；排队满则记录容量流失。
2. 处理排队耐心和待出餐等待，超时客人离开，订单作废。
3. 为空桌分配队首客人；只从“已激活 + 已上架 + 厨师能做”的菜里点单。
4. 为有空灶眼的订单开始烹饪，按 `基础秒数 ÷ 厨师速度倍率` 减少剩余时间。
5. 烹饪完成后进入待出餐区；甜甜圈效果存在时自动出餐。
6. 处理用餐、结账、现金与材料掉落；更新今日客流和营业额。
7. 递减礼物持续时间与冷却；清理已结束效果。
8. 追加可读日志，发布新的只读 state。

刷新页面只恢复 `resources + progress + 配置版本`，在线客人、订单、灶眼和礼物计时全部重建，避免回档或重复结账。

## 4. 数据驱动配置

建议 `src/game-data/` 只放纯数据，不放 UI 逻辑：

```text
restaurantLevels.ts  // 1~3级容量、客流和升级消耗
chefs.ts             // 可做品级、速度倍率和升级条件
dishes.ts            // 12道菜、价格、烹饪秒数、研发消耗
guests.ts            // 6类客人、权重、耐心、溢价、掉落率
gifts.ts             // 五种礼物的固定规则和上限
pillRewards.ts       // 23/23/23/12/8/11 概率表
```

业务层只读取配置，不在组件中写死数值。所有随机抽取都接受可注入的 RNG；默认使用 `Math.random`，测试使用固定种子或 mock RNG。

## 5. 弹幕与礼物设计

### 模拟弹幕

输入框支持：

- `出餐`：端出待出餐区最早订单。
- `排1` / `排2` / `排3`：P1 功能，调整队列优先级；默认不影响 P0 自动经营。
- `暂停`、`1倍`、`2倍`、`5倍`：调试命令。

每条指令显示为日志和短暂浮层，保证“事件进来 → 状态变化 → 画面反馈”能被评审看见。

### 五种礼物

- **红色仙女棒**：当前烹饪订单剩余时间减少该菜基础烹饪时长的 20%，最多 4 根，剩余时间最低保留 20%。无烹饪订单时不消耗。
- **能量药丸**：按 GDD 概率表抽取；第 10 抽若存在可激活新菜则保底激活，否则转为三色材料各 2 个。
- **魔法镜**：最多 3 层，持续 30 秒；1/2/3 层客流倍率为 1.5/2.0/2.5，重复送刷新时间，不突破队列和桌位上限。
- **甜甜圈**：增加 60 秒自动出餐时间，最多预存 180 秒；待出餐订单出现后立即处理。
- **炸弹**：冷却 20 秒；至少 3 个空位且有可做菜时，招揽 `min(3 + 饭馆等级, 空桌 + 空排队位)` 个客人，其中 30% 向下取整为当前可服务最高品级客人。

平台规则层面，正式接入时应避免把随机效果包装成“抽奖/盲盒”，并对概率做公开说明；本地 Demo 仍按题目要求实现“能量药丸”，README 中明确这是离线模拟规则。[抖音直播玩法准入规则](https://partner.open-douyin.com/docs/resource/zh-CN/interaction/introduction/live-play/creation)

## 6. H5 页面结构

基准画布采用 **9:16 竖屏构图**，桌面浏览器中居中显示，窄屏时按宽度缩放；不把响应式适配扩展成额外系统。

```text
┌──────────────────────────────┐
│ 级别 / 厨师 / 现金 / 材料 / 今日营业 │  顶部资源栏
├──────────────────────────────┤
│ 排队区 → 3~5 个位置            │
│                                │
│ 桌位区：座位状态、客人、剩余时间 │  主场景
│                                │
│ 灶眼区 → 烹饪进度              │
│ 待出餐区 → [出餐]              │
├──────────────────────────────┤
│ 菜单/研发 │ 饭馆/厨师升级 │ 礼物 │  面板
├──────────────────────────────┤
│ 模拟弹幕输入 + 可滚动事件日志   │
└──────────────────────────────┘
```

组件边界建议：

- `ResourceBar`：只读资源。
- `RestaurantBoard`：排队、桌位、灶眼、待出餐。
- `MenuPanel` / `UpgradePanel`：发出研发和升级命令。
- `GiftPanel`：发出礼物命令并显示冷却/持续。
- `DanmakuPanel`：输入模拟弹幕、显示事件日志。
- `DebugControls`：暂停和倍速。

## 8. 24 小时排期与验收

- **0–2 小时**：定义类型、配置表、状态图和存档 schema。
- **2–7 小时**：完成 Tick、到访、排队、落座、点单、烹饪、出餐、结账、流失。
- **7–12 小时**：完成主场景、资源栏、事件日志、暂停和倍速。
- **12–17 小时**：完成研发、饭馆/厨师升级、五种礼物和药丸保底。
- **17–21 小时**：补 Vitest、localStorage、边界提示，逐条跑 T01–T14。
- **21–24 小时**：整理 README、构建、录屏/GIF、检查离线打开和刷新恢复。

最小测试集：

- 容量：队列满不入队，炸弹不突破空位。
- 时间：排队耐心、待出餐等待、烹饪速度和倍速都来自同一 Tick。
- 经济：无效礼物不扣资源；结账不重复；刷新不回档。
- 概率：药丸概率合计 100%，第 10 抽保底成立；固定 RNG 可复现。
- 上限：仙女棒 4 根、魔法镜 3 层、甜甜圈 180 秒、炸弹 20 秒冷却。
- 成长：饭馆/厨师升级同时改变容量、客流、可做品级和速度。

## 9. 已知风险与决策

- **参考案例规则不透明**：只借鉴交互形态，不依赖它的未公开数值；座位排序的拖拽/优先级做成 P1。
- **24 小时范围容易失控**：先完成无礼物也能自动经营的闭环，再加互动。
- **直播平台限制**：Demo 不接真实抖音数据；未来通过 `CommentAdapter`、`GiftAdapter` 替换本地事件即可。
- **动效成本**：只做状态变化的短 Tween、进度条和浮层，不让动画拥有业务计时权。
